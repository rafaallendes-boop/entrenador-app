Este runbook cubre lo que no se puede demostrar con vitest: RLS efectiva,

- `CLIENT_ERROR_INGESTION_ENABLED` **sin definir** o en `false` (por defecto la
  ingesta está apagada; se enciende recién en el paso 4).
- Dos cuentas reales del proyecto, A y B, con sus UUID a mano.
- `SUPABASE_SERVICE_ROLE_KEY` disponible sólo en el entorno de Functions.

## 1. RLS y grants

Correr `supabase/queries/2026-09-06-035-rls-checks.sql` con `psql`, reemplazando
antes los dos UUID de fixture por los de A y B.

| Caso | Esperado |
|---|---|
| Precondiciones | tabla, RLS activada y RPC presentes |
| Policies | exactamente una, `client_error_events_select_own`, SELECT |
| Grants | `authenticated` sólo SELECT; `anon` sin ninguno |
| EXECUTE de la RPC | cero filas para `anon` y `authenticated` |
| Caso 1 | A ve 1 fila propia vigente |
| Caso 2 | A no ve su fila de 31 días |
| Caso 3 | A no ve ninguna fila de B |
| Caso 4 | `anon` recibe error de permisos o 0 filas |
| Caso 5 | INSERT, UPDATE, DELETE y EXECUTE fallan con permiso denegado |
| Caso 6 | conteo secuencial: se rechaza al llegar a 30 en la ventana |

**El bloque termina en `rollback`:** no deja fixtures. Si algo lo interrumpe,
verificar que no quedaron filas con `release = 'r-test'`.

> Una consulta corrida como superusuario o con `service_role` **no demuestra
> RLS**: esos roles la saltan. Los casos 1 a 5 sólo valen ejecutados con
> `set local role authenticated` y su `request.jwt.claims`.

## 2. Ausencia de carrera en el techo

El caso 6 del SQL es secuencial y **no** demuestra que no haya carrera. Para eso,
31 conexiones simultáneas contra la misma cuenta:

```bash
# Requiere psql y una cuenta de prueba sin eventos en la última hora.
USUARIO="00000000-0000-0000-0000-00000000000b"
for i in $(seq 1 31); do
  psql "$DATABASE_URL" -At -c \
    "select inserted from public.insert_client_error_event(
       '$USUARIO','self','window_error','unknown',
       lpad(to_hex($i),16,'0'),'TypeError',null,null,'/week',null,
       'r-test','web',30,3600)" &
done
wait
```

Después:

```sql
select count(*) from public.client_error_events
 where user_id = '…b' and release = 'r-test' and created_at > now() - interval '1 hour';
```

**Criterio: el conteo es exactamente 30, nunca 31.** Si diera 31, el
`pg_advisory_xact_lock` no está serializando y el techo es decorativo.

Limpieza: `delete from public.client_error_events where release = 'r-test';`
(como `service_role`).

## 3. Atribución de identidad sobre HTTP

Esto pertenece al endpoint y **no se demuestra con SQL**: verifica que el
`user_id` del payload se descarta y manda el de la sesión.

Con un JWT real de la cuenta A y `CLIENT_ERROR_INGESTION_ENABLED=true`:

```bash
curl -i -X POST "$SITE/.netlify/functions/report-client-error" \
  -H "Authorization: Bearer $JWT_DE_A" \
  -H 'Content-Type: application/json' \
  -d '{"source":"react_boundary","diagnostic_code":"render_failure",
       "scope_kind":"self","error_name":"TypeError","component":"PlanBuilderV2",
       "route":"/plans/builder","release":"r-test","platform":"web",
       "user_id":"UUID_DE_B","message":"rafa@example.com","stack":"crudo"}'
```

Esperado: **204 sin cuerpo**. Después, con inspección privilegiada:

```sql
select user_id, route, error_name, component, stack_frames
  from public.client_error_events where release = 'r-test'
 order by created_at desc limit 1;
```

**Criterios, todos obligatorios:**

- `user_id` es el de **A**, no el de B.
- No hay rastro de `rafa@example.com` ni de `crudo` en ninguna columna.
- `stack_frames` es `null` (el release `r-test` no tiene manifiesto).
- `route` es `/plans/builder`.

Repetir con `route: "/inventada"` → debe quedar `unknown` y responder 204, no 400.

## 4. Contrato y límites

| Petición | Esperado |
|---|---|
| Sin `Authorization` | 401 |
| Método `GET` | 405 |
| `{"source":"inventada",…}` | 400, y **cero filas nuevas** |
| Cuerpo > 8 KiB | 413, y cero filas nuevas |
| Payload válido con la ingesta apagada | 204 y **cero filas** |
| 31ª petición válida en una hora | 204 (igual que un éxito) y cero filas nuevas |

La última es deliberada: éxito y descarte por cupo son indistinguibles para el
cliente, para que no tenga material con el que reintentar.
